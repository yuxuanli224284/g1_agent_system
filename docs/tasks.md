# 任务定义

本页说明 g1_agent_system 要完成的几个任务：任务 1（找箱并接近）、任务 2（把扫码枪放到条码前）、任务 3（找箱后按固定顺序扫完所有条码），以及任务 3 后来扩展出的落地箱堆、多面箱堆、无码面和纸箱贴纸等场景。每个任务都写明输入、目标、成功判据和评测指标，最后按时间记录任务定义怎样随需求变化。

任务定义分散在几处：需求方的三份任务书（仿真环境、agent 系统、测试集，不随仓库发布）、三份任务配置（`configs/task1.yaml`、`task2.yaml`、`task3.yaml`）、Harness 的记账规则（`g1agent/harness/guards.py`）、评测器（`g1agent/eval/evaluator.py`、`g1agent/eval/scan_order.py`），以及仿真侧测试集里的场景文件（`g1_barcode_sim/suites/*/`）。本页把它们放在一起说明。路径都相对 `g1_agent_system/`，另有说明的除外：三份任务书在本仓库的上一级目录，`g1_barcode_sim/` 是仿真包，不在本仓库内。

## 作用与在系统中的位置

"任务"本身没有单独的代码模块。它由下面几部分共同确定：

- 场景文件指定要跑哪个任务、机器人从哪里出发、目标是哪个箱子、要扫哪几个面；
- 任务配置给出算法参数、预算和评测容差；
- Harness 决定这个任务能用哪些工具，并按台账判断成败；
- 评测器用真值判断成败。

| 组件 | 从任务定义拿到什么 | 位置 |
|---|---|---|
| 场景文件（测试集） | `task`（1/2/3）、`target`（`left`/`right`/`all`）、`robot_init`（起始距离、横向偏移、偏航角）、`scan_faces`（`"all"` 表示扫箱堆四个面）、箱子与条码布局 | `g1_barcode_sim/suites/<套件>/scenarios/*.json` |
| 运行入口 | 读场景，决定任务编号（`--task 3` 可以把任务 1 的场景当任务 3 跑）、目标选择器和是否多面 | `scripts/run_task.py` 中的 `run()` |
| 任务配置 | 算法参数、预算、评测容差。任务 3 通过 `inherits` 继承任务 1、2 | `configs/task1.yaml`、`task2.yaml`、`task3.yaml`，合并逻辑在 `g1agent/common/config.py` |
| 工具层 | `Toolbox._c1()` / `_c2()` 按 `Toolbox.task` 选用任务 1/2 或任务 3 的参数 | `g1agent/tools/toolbox.py` |
| Harness | 每个任务可用的工具（`TASK_TOOLS`）、预算、任务 3 的阶段标记、成败台账 | `g1agent/harness/registry.py`、`guards.py` |
| 编排器 | 开场任务说明（例如"这次要扫箱堆的每一个面"） | `g1agent/orchestrators/agent_full.py` 中的 `_start_text`、`phase1_summary` |
| 评测器 | 用真值判定成功，计算误差拆分和扫码指标 | `g1agent/eval/evaluator.py`、`g1agent/eval/scan_order.py` |

成败有两套判定，含义不同：

- **Harness 判定**（`harness_success`）只用算法自己的估计值，是系统对自己结果的报告，日志里记为 `harness_finish`；
- **评测判定**（`eval_success`）由评测器经评测端口读真值后计算，算法代码拿不到真值（见[机器人接口与仿真服务器](robot_interface.md)中的"真值隔离"一节）。实验结果以评测判定为准。

## 当前实现

### 任务一览

| | 任务 1：找箱并接近 | 任务 2：扫码枪就位 | 任务 3：找箱 + 按顺序扫完所有条码 |
|---|---|---|---|
| 起点 | 离桌沿 2–5 m（场景 `robot_init`） | 真值观察位加噪声（测试集生成规则见下） | 离箱子或箱堆约 2.5 m（箱堆场景），或任务 1 的起点 |
| 输入 | 头部 RGB-D、场景给的目标 `left`/`right` | 同左，加腕部（扫码）相机 | 同左；目标固定为 `all`；多面场景另有 `scan_faces: "all"` |
| 目标 | 走到目标箱面前的观察距离 d_obs，整个箱面在头部画面内 | 扫码枪枪口停在条码法向前方 0.20 m，扫描方向对准条码 | 视野内所有条码各扫一次，顺序为"列从左到右，列内从上到下"；多面时按 正面→右→背→左 绕箱堆 |
| Harness 判据 | 沿法向距离误差 < 3 cm，偏航 < 3°，箱面在画面内 | 距离误差 ≤ 2 cm，偏轴 < 2 cm，夹角 < 10° | 计划非空，每个计划条目都是 `scanned` 或 `unreadable`，多面时四个面都走过 |
| 评测判据 | 距离误差 < 5 cm，偏航 < 5°，真值箱面四角在画面内 | 距离误差 ≤ 3 cm，偏轴 < 3 cm，夹角 < 15° | 每个真值条码都读到、顺序正确、没有读到别的内容；多面时另有面的顺序要求 |
| 预算 | 40 次工具调用、6 步探索、单工具重试 2 次、1800 s | 同左 | 阶段 1 同左；规划后每个条码追加 28 次调用和 600 s |

### 场景文件与任务指令

运行入口 `scripts/run_task.py` 的 `run()` 按以下规则从场景文件得到任务：

1. 任务编号取场景的 `task` 字段。命令行 `--task` 可以覆盖它，例如用 `--task 3` 把桌面两箱的任务 1 场景当任务 3 跑。覆盖只影响 agent 和评测，仿真器仍按原场景复位。
2. 目标选择器：任务 1、2 用场景的 `target`（`left` 或 `right`）；任务 3 一律用 `task3.yaml` 的 `selector_default: all`，场景里的左右目标不用。
3. 多面开关：`tb.multi_face = (task == 3 and 场景.scan_faces == "all")`。代码注释把它定义为"任务指令"，不是真值：它告诉机器人"这次要扫箱堆的每个面"，但不告诉它哪个面有码。没有这个字段时只扫朝向机器人的那一面。
4. 任务 3 运行中，Harness 第一次发出 `task1_end` 阶段标记时，`run()` 会把当时的 `root_target` 复制一份（`task1_end_root_target`）。评测任务 1 阶段时用这份副本，因为扫码阶段可能重新计算 `root_target`。

`agent_full` 编排器的开场消息由 `_start_text()` 生成：

- 任务 1、2：`Start task {n}. Target: the {selector} box.`
- 任务 3：`Start task 3 (phase 1: find all boxes and approach them).`，后面接一句范围说明。多面时说明"要扫每一面，某一面扫完时 `next_barcode` 返回 `face_done`，然后调用 `go_to_next_face` 和 `plan_scans`"；单面时说明"只扫面对你的这一面"。

阶段 1 结束后，上下文会被压缩成一条摘要（`phase1_summary`）。摘要的第一行原样重复开场时的任务说明，原因见演进记录 v8。

### 任务 1：找箱并接近到观察距离

**输入与目标。** 机器人在离桌沿 2–5 m 处出发，桌上并排两个箱子，场景指定目标是左箱还是右箱。机器人要找到目标箱，走到它前表面正前方的观察位姿：朝向正对箱面，离面距离为 d_obs，而且整个箱面落在头部相机画面内。

**d_obs 的定义**（`Toolbox.compute_obs_pose`）：在 `d_obs_range: [0.60, 1.00]` m 内按 `d_obs_step: 0.05` 从小到大试，共 9 档。取第一个让箱面四角都投影在头部图像内、并留 `perception.yaml` 中 `fov_margin_frac: 0.05` 边距的距离。没有满足条件的档位时取上界 1.00 m，返回 `partial`。

**步骤**（`orchestrators/rule.py` 的状态机，数值来自 `task1.yaml`）：

1. `look_head` + `detect_boxes`。
2. `select_target_box`：按检测框在图像中的左右顺序选。只看到一个箱子时无法判断它是左还是右，返回失败。
3. `fit_front_face`：在检测框内用深度做 RANSAC 平面拟合。内点太少时，朝检测方向前进 `too_few_inliers_advance_m: 1.0` 再试。
4. `compute_obs_pose`：按上面的规则得到 d_obs 和 root 目标。
5. `approach`：分段走。每段走 min(剩余 × 0.5, 1.0 m)，剩余不到 0.3 m 时以半速一次走完，最多 8 段，每段后重新感知目标。
6. 到位检查 `arrive_check`：沿法向距离误差 < `dist_tol_m: 0.03`，偏航 < `yaw_tol_deg: 3.0`，箱面在画面内。不满足时最多微调 `max_fine_tunes: 2` 次。
7. 看不到目标时，rule 模式按 `explore_sequence` 探索：`forward 0.5` → `left 0.5` → `right 1.0` → `back 0.5` → `turn_left 15` → `turn_right 30`。`agent_*` 模式下由 LLM 选方向和距离。

**可用工具**（`registry.py` 中的 `TASK1_TOOLS`）：`look_head`、`detect_boxes`、`select_target_box`、`fit_front_face`、`compute_obs_pose`、`approach`、`check_face_in_view`、`explore`、`finish`。条码和手臂工具不开放给任务 1，原因见 v2。

**评测**（`evaluator._task1`，容差在 `task1.yaml` 的 `eval` 中）：

- `d_err_m` = |机器人 root 到真值目标箱面平面的水平距离 − Harness 选定的 d_obs|。注意比较对象是 Harness 自己选的 d_obs，不是真值观察位的 d_obs；
- `yaw_err_deg` = 机器人朝向与"正对真值箱面"朝向之差；
- `face_in_view_gt`：真值箱面四角都投影在头部图像内（边距为 0）；
- 成功 = `d_err_m < 0.05` 且 `yaw_err_deg < 5.0` 且 `face_in_view_gt`；
- 误差拆分（只报告，不参与判定）：感知误差 `perception_err_pos_m` 是 Harness 目标（红标记）与真值观察位（绿标记）之差，执行误差 `execution_err_pos_m` 是实际位置（黄标记）与 Harness 目标之差。

Harness 判据（3 cm / 3°）比评测判据（5 cm / 5°）紧。任务书给的理由是：Harness 只能用估计值判断，要留出估计误差。

### 任务 2：把扫码枪枪口放到条码前

**输入与目标。** 机器人从任务 1 的结束位姿附近出发。测试集里，起点是真值观察位加噪声：L0 无噪声，其他级别为 ±0.03 m / ±3°，`start_noise` 因素线性放大到 ±0.08 m / ±8°。机器人要找到目标箱面上的条码，把扫码枪枪口（手腕参考点）放到 p = c + 0.20·n：c 是条码中心，n 是箱面外法向；扫描方向（枪口前向）取 −n。

**步骤**（任务书 4.3，数值来自 `task2.yaml`）：头部检测条码（检测不到时前进 0.10 m 再试一次）→ 像素射线与箱面平面求交得到条码中心 → `compute_wrist_target` → `plan_stance`（以条码为参照的站位网格：离面 0.35–0.70 m，横向 ±0.40 m，步长 0.05 m）→ `approach('stance_target')` → `move_arm('pre')`（预备位在 0.30 m）→ `refine_with_wrist`（腕部相机修正）→ 可选的 `stereo_check_wrist`（基线 0.04 m，差异超过 0.02 m 时报警）→ `move_arm('final')` → `check_wrist_placement`。每一步的实现见[工具箱](toolbox.md)一页。

**可用工具**（`TASK2_TOOLS`）：除任务 3 专用的 `plan_scans`、`next_barcode`、`go_to_next_face` 之外的全部工具。

**Harness 判据**（`task2.yaml` 的 `check`）：枪口到条码平面的距离与 0.20 m 之差 ≤ 0.02 m，条码中心偏离扫描轴 < 0.02 m，扫描轴与 −n 的夹角 < 10°。有条码长轴信息时，另查 roll 误差（扫描图像水平轴与条码长轴的夹角），容差同样是 10°。

**评测**（`evaluator._task2`，容差在 `task2.yaml` 的 `eval` 中）：

- `wrist_dist_to_plane_m`、`wrist_axis_offset_m`、`wrist_angle_err_deg` 由 `wrist_metrics()` 按真值条码中心和法向计算；
- 成功 = |距离 − 0.20| ≤ 0.03 且偏轴 < 0.03 且夹角 < 15°；
- 误差拆分：头部感知误差 `head_perception_err_m`（蓝标记对绿标记）、腕部感知误差 `wrist_perception_err_m`（紫对绿）、执行误差 `execution_err_m`（黄对紫）。

任务 2 本身只要求就位，不要求扫码。在任务 3 里，`scan` 工具在就位后触发扫码枪（见下）。

### 任务 3：找箱后按固定顺序扫完所有条码

任务 3 不在原任务书里，是 2026-11-06 按需求新增的。它把任务 1 和任务 2 合在一起，分两个阶段。

**阶段 1（找箱）。** 目标选择器为 `all`：观察位姿要覆盖所有检测到的箱子。参考点由 `Toolbox._faces_reference` 计算：

- 横向取所有角点的中点；
- 沿法向取离机器人最近的那个面；
- 高度取各面中心的平均。

走完后做到位检查，只看沿法向距离、偏航和箱面是否都在画面内，不看横向偏移。检查不过时返回 `partial`，提示"阶段 1 结束，下一步调用 plan_scans"，不判失败。这就是需求里的"快速结束"：扫码阶段会自己规划站位，阶段 1 不必精确到位。

**阶段 2（扫码）。**

1. `plan_scans` 在当前视角下检测所有箱面上的标签，并按固定规则排序，生成扫码计划。每个条目的状态初始为 `pending`。
2. 循环 `next_barcode` 取下一个条码。对每个条码走任务 2 的流程，最后调用 `scan`。
3. `scan` 读到的内容按内容去重：一个内容只记第一次，后面再读到同一内容，当前条码记为 `duplicate`，不重复计数。
4. 每处理完一个条码，`next_barcode` 都会先从当前位置重看一次（`_plan_update_from_here`）。新发现的标签插入计划中尚未扫的部分，已扫的条目不动。

**扫码顺序规则**（`g1agent/tools/scan_order.py` 的 `column_order`；评测端 `g1agent/eval/scan_order.py` 有一份独立副本，`tests/test_task3_logic.py` 检查两份结果一致）：

- 在规划时的 root 坐标系里（左为 +y），两个标签的横向范围严格重叠，就属于同一列。列是这种重叠关系的连通分量；
- 列从左到右排，列内按高度 z 从上到下排；
- 高度相同时，依次按横向中心、键名排序，保证顺序确定；
- 顺序由工具给出，LLM 不能修改。

需求原话是"从左往右、从上往下"。把它解释成"列"是我们的设计决定。

**条码状态**（`ws.barcodes[id].status`）：

| 状态 | 含义 | 由谁设置 |
|---|---|---|
| `pending` | 计划中，还没处理完 | `plan_scans` |
| `scanned` | 读到一个新内容 | `scan` |
| `duplicate` | 读到的内容之前已被别的条码读过 | `scan` |
| `failed` | 尝试过但没读到，`next_barcode` 时仍是 `pending` | `next_barcode`、`finish` |
| `unreachable` | 所有身体高度档位下都找不到鲁棒站位，附原因（标签高度、太高还是太低、骨盆高度、行走容差） | `plan_stance` |
| `unreadable` | 在扫码距离上、整个标签在视野内，整幅画面什么码也没解出，之前的腕部画面也从未读出过 | `scan` |

**扫码距离（stand-off）。** 任务 1、2 用固定的 0.20 m（`standoff.mode: fixed`）。任务 3 用自适应距离（`standoff.mode: adaptive`）：

d = symbol_width / (2·tan(hfov/2)) / fill_frac，再限制到 [`min_m 0.12`, `max_m 0.30`] m。

- hfov 由腕部内参算出：fx 1087、宽 640 px，对应 32.8°；
- symbol_width 指印刷的符号本身，不含白色底板；
- `fill_frac 0.68` 的取法：让标称 0.08 m 的 code128 符号正好落在已验证的 0.20 m（0.08 / (2·tan 16.40°) / 0.20 = 0.679）；
- 规划站位时宽度用头部估计（偏大，所以偏保守）。头部估计只能把距离拉远，不能拉到 0.20 m 以内。到预备位后改用腕部实测值（解码出的符号轮廓投影到箱面上的宽度），再去最终位；
- `min_m 0.12` 来自需求中的决定；`max_m 0.30` 没有单独的依据。

**预算**（`task3.yaml` 的 `budget`，由 `guards.Harness._after` 执行）：

- 阶段 1 与任务 1 相同：40 次调用、6 步探索、单工具重试 2 次（同一工具连续失败 3 次后，再调用会被拒绝）、1800 s；
- 每次 `plan_scans` 成功后重新计算：`max_tool_calls = 40 + n × 28`，`max_wall_s = 1800 + n × 600`，n 是当前计划条目数。以 12 个码的四面箱堆为例，上限是 376 次调用、9000 s；
- 28 次的来历：任务 2 在 rule 模式批量运行中实测最多 21 次调用（配置注释记为 57 个 episode，存档的 `results.csv` 里是 56 个，见 v2），再加 `next_barcode` 1 次、`scan` 1 次、一次读不到时的重试 3 次（refine、final、scan）、手臂回 home 前后各 1 次；
- 600 s 的来历：同一批 episode 实测最长 518 s（p90 为 324 s），再加扫码重试和两次手臂回 home（各约 3 s），向上取整；
- 失败计数按条码算：`next_barcode` 切到下一个条码时清零。切换面（`face_done`）时不清零，否则一个反复失败的 `go_to_next_face` / `plan_scans` 循环永远碰不到重试上限。

**阶段标记**（`guards.py`，写进日志并通过评测端口记录）：`task1_end`（第一次 `plan_scans` 成功时，或在此之前就 `finish` 时）、`barcode_start`、`barcode_end`（带状态和原因）、`face_start`、`face_end`（多面）、`scan_done`。

**Harness 判定**（`guards.Harness._finish`）：

- 调用方在 `finish` 里自报的成功另存为 `claimed_success`，不作为结果；
- `success` = 至少一个条目是 `scanned`，所有条目都是 `scanned` 或 `unreadable`，并且（多面时）巡视顺序上没有剩下的面；
- 计划或巡视还有剩余工作时，`finish(success=true)` 会被拒绝；
- `failed`、`unreachable`、`duplicate`、`pending` 都使 Harness 判定为失败。

**评测判定**（`evaluator._task3`）：

1. 期望集合：所有非干扰项（`distractor` 为假）的真值条码。条码内容必须唯一，否则直接报错，因为按内容评测无从定义。
2. 期望顺序：
   - 单面：在 `task1_end` 时刻的真值 root 系下，用同一列规则排序（`order_frame = "task1_end"`）。没到 `task1_end` 时，用起始位姿（`"robot_init"`）；
   - 多面（真值 `faces` 里有不止一个面带码）：先按巡视顺序 `FACE_TOUR = ("-x", "-y", "+x", "+y")`（正面、右、背、左）排面，每个面在它自己的理想坐标系（`face_frame`，原点在该面的真值观察位）里按列规则排序（`order_frame = "faces"`）。
3. 读码记录来自仿真器的扫码日志：每次 `scan()` 都有记录，包括真值扫描射线击中的标签和枪口位姿。一个内容只在第一次读到时计数。
4. 每次读码的就位误差：枪口相对"真值条码中心 + d_gt·n"的误差。d_gt 用真值符号尺寸（`pattern_size` 的长边）和仿真扫码相机的真值 hfov，代入同一个 stand-off 公式算出。就位合格（`placement_ok`）沿用 `task2.yaml` 的评测容差。
5. 成功条件：
   - 单面：所有期望条码都读到，顺序与期望顺序完全一致，没有读到期望集合以外的内容；
   - 多面：所有期望条码都读到，每个面内顺序正确，第一个读到的面是第一个带码的面（`front_first`），各面连续扫完、不来回（`faces_contiguous`），没有读到外来内容。整条巡视顺序是否完全一致（`face_order_ok`）只报告，不参与判定；
   - 任务 1 阶段的到位精度单独报告为 `t1_success` 等字段，不参与任务 3 的成败。这条规则来自 2026-11-06 的需求（让阶段 1 尽快结束、进入扫码）：阶段 1 按设计会提前结束，扫码阶段自己规划站位。

评测输出的主要字段：`n_gt_barcodes`、`n_scan_calls`、`n_no_read`、`n_scanned_distinct`、`scan_recall`、`wrong_contents`、`n_duplicate_reads`、`n_read_not_aimed`（读到的内容不是扫描射线对准的那个）、`order_ok`、`order_ok_scanned`（只看已读到的码，顺序是否正确）、`tip_err_mean_m` / `tip_err_max_m`、`n_placement_ok`、`n_planned`、`plan_status`、`reported_unreachable`、`ledger_matches_log`（Harness 台账与仿真器扫码日志是否一致）；多面时另有 `per_face`、`face_order`、`front_first`、`faces_contiguous`、`face_order_ok`。

**扫几个面。** 系统不预先知道哪个面有码。`scan_faces: "all"` 的含义是"四个面都要走到、都要看"。某个面拟合成功但没检测到标签，是合法结果，这个面按空计划处理，不算失败。没有这个字段时只扫正面。

**底层码的高度。** 扫码枪保持水平时，离线 `plan_stance` 测得最深标定下蹲档位下最低能稳定够到约 0.27 m。所以场景按"码中心不低于约 0.27 m，取 0.30 m 左右"贴底层码。四面箱堆的底层码又提到 0.33 m，原因是要求扫码画面与条码对齐之后，0.30 m 够不到（见 v8）。

**扫码画面对齐。** 从 3×3 箱堆开始，需求要求扫码相机画面的水平轴与条码长边平行，转 180° 也算对齐。工具层用 `_long_axis` 给 IK 加 roll 约束，`check_wrist_placement` 检查 roll 误差（容差 10°）。仿真扫码器同时改成只解码原始画面、不再旋转图像，所以没对齐就读不出来。评测器的 `placement_ok` 不含 roll，roll 是否对齐体现在能不能读出码。

**贴纸与 `unreadable`。** 纸箱模型的贴图上有小条码贴纸、"PARCEL POST" 贴纸和大张面单，印着解不出来的假条码。从头部相机看，它们和真码区分不开（见 v10），只能走近后用腕部相机确认。所以：

- 评测器只看真值条码，贴纸不在期望集合里，不影响评测判定；
- Harness 会把贴纸当成计划条目逐个核验。能确认读不出的记为 `unreadable`，不算失败；确认不了的（例如面单比视野还宽）如实记为 `failed`，此时 Harness 判定为失败。

### 配置文件与继承

- `task1.yaml`、`task2.yaml` 各自独立；`task3.yaml` 写 `inherits: [task1, task2]`。
- `g1agent/common/config.py` 按 `inherits` 的顺序取父配置的顶层键，再用本文件的顶层键覆盖。合并是浅合并：`standoff`、`budget` 这样的嵌套项整体替换。
- 两个父配置对同一个键给出不同值、而子配置没有显式设置时，抛出 `ValueError`，不允许"最后一个父配置胜出"的静默覆盖。task1 和 task2 的 `eval` 不同，所以 task3 必须自己写 `eval`：阶段 1 用 0.05 m / 5°，与任务 1 相同；每次读码的就位检查沿用 `task2.yaml` 的 `eval`。
- 检测到继承环时也抛出 `ValueError`。
- 工具层通过 `_c1()`、`_c2()` 取参数：任务 3 时两者都返回合并后的 `cfg["task3"]`。

### 每个任务可用的工具

`g1agent/harness/registry.py`：

```python
TASK1_TOOLS = ["look_head", "detect_boxes", "select_target_box", "fit_front_face", "compute_obs_pose", "approach",
               "check_face_in_view", "explore", "finish"]
TASK3_ONLY = ["plan_scans", "next_barcode", "go_to_next_face"]
TASK2_TOOLS = [n for n in TOOLS if n not in TASK3_ONLY]
TASK_TOOLS = {1: TASK1_TOOLS, 2: TASK2_TOOLS, 3: list(TOOLS)}
```

Harness 收到不属于当前任务的工具调用时，返回 `fail`，原因为 `tool '<name>' is not part of task <n>`，并标记 `rejected`。`agent_full` 发给 LLM 的工具定义也只包含当前任务的工具。

`scripts/run_suite.py` 每个场景写一行 `results.csv`，字段包括：`harness_success`、`eval_success`、任务 1 的 `d_err_m` / `yaw_err_deg` / 感知与执行误差、任务 2 的 `wrist_dist_to_plane_m` / `wrist_axis_offset_m` / `wrist_angle_err_deg` / 三段误差、`tool_calls`、`explore_steps`、`llm_calls`、token 数、`llm_length_truncations`（截断次数）、`wall_s`、`failure`。任务 3 的完整评测结果在每个场景目录的 `result.json` 里。`scripts/summarize.py` 汇总成 `report.md`。

### v3 · 2026-11-06 · 任务 3 初版：合并任务 1、2，扫完所有码

**需求。** 先在最简单的场景上把任务 1 和任务 2 合起来，并调试 agent 系统。具体要求：

1. 用 agent 系统把任务 1、2 合起来跑一轮；
2. 任务 1 可能不知道什么时候算结束，要加判断，让它尽快结束、进入任务 2；
3. 扫码枪是不是停得太远，该不该更近；
4. 面前有 2 个箱子或 2 个码时先扫哪个还没实现。硬性规定：在所有能识别的码中，按从左往右、从上往下的顺序扫；
5. 一个码只能成功扫一次，重复扫到不算。

之后需求方又决定"算法本身没有检测框就不要了，按推荐的扫码枪距离来"，也就是采用自适应距离。

**当时的设计。**

- **阶段 1**：选择器 `all`，观察位姿覆盖所有箱面的并集。到位判据只看沿法向距离、朝向和箱面是否全在画面内，不看横向。走完没到位也直接进入扫码阶段（`partial`），只要定位到至少一个标签就继续。
- **阶段 2**：`plan_scans` 一次定位所有标签并排序（列规则），然后循环 `next_barcode`。顺序由工具决定，LLM 不能改。按内容记账，一个内容只算一次。
- **扫码距离**：自适应，d = w / (2·tan(hfov/2)) / 0.85，限制在 [0.12, 0.30] m。0.85 的取法是让标称 0.10 m 的标签（含白色底板）落在已验证的 0.20 m。
- **Harness 成功**：计划非空，每个条目都是 `scanned`，出现 `duplicate` 或 `failed` 都算失败。自报结果另存为 `claimed_success`。
- **评测成功**：只看扫码，即全部读到、不重复计数、顺序正确、没有读错。任务 1 阶段的到位精度单独报告。
- **预算**：阶段 1 沿用任务 1，规划后每个条码追加 28 次调用、600 s（依据见上文）。
- **配置**：`configs/task3.yaml` 用 `inherits: [task1, task2]`。`config.py` 在两个父配置冲突时报错，迫使 task3 显式写 `eval`。

|---|---|---|---|
| rule | 2/2 扫到，顺序正确；任务 1 阶段停在 6.9 cm 外（旧的 `final_bias_m`，已去掉） | 542 s | 0 |

**遇到的问题。**

- `agent_full` 在离箱子 0.67 m 处向前探索 0.5 m，躯干撞上箱子。改为 `explore` 拒绝终点离面小于 `min_face_dist_m 0.35` 的移动。

### v4 · 2026-11-07 · stand-off 改按印刷符号宽度定义，最终距离以腕部实测为准

**问题。** 任务 3 首轮所有模式下枪尖都偏远约 4 cm：t1_L0_0000 上误差 4.0 cm，扫码距离算成约 0.24 m，而不是 0.20 m。

**修改。**

- 重新定义 symbol_width：只算印刷符号（条和模块），不含白色底板。理由是扫码枪要装下并分辨的是符号，而且有没有底板符号都在。

- 评测端相应改为按真值 `pattern_size` 计算 d_gt。
- 站位规划多检查一项：手臂能否伸到最近距离 0.12 m。

**首轮问题（`stack4c_L0_0001`，`agent_full`，4055 s）。** 真码只扫到 4/6，漏了正面底层和背面中层。面的顺序正确，没有读错或重复读。我们把问题分成三类：

1. **贴纸假条码被检测成标签。** 检测器在纸箱面上检出 35 个框，其中 29 个是贴纸。我们在 4 个面、8 个视角上比较了检测分数、条纹方向一致性、宽度和 4 种检测提示词：从头部相机看，真码和贴纸的这些特征完全重叠，区分不开。唯一可靠的办法是走近后用腕部相机解码。
2. **真码漏检。** 原来的下蹲补看只选"看底部最细"的那一档（0.25 m 深蹲）。逐档实测（11 档 × 2 面）发现，在纸箱纹理上这一档一个下层真码也找不到，而 0.45–0.60 m 几档在两面都各检出 2 个真码，召回率与高度不是单调关系。
3. **真码读不出**，以及测试中暴露的执行问题，见下。

**修改。**

- 新增 `unreadable` 结果，用来区分"确认无码"和"没扫成"。判定要同时满足：
  - 枪口在扫码距离上，误差不超过就位检查容差 2 cm；
  - 整个标签在扫码视野内；
  - 整幅画面什么都没解出，之前任何腕部画面也没解出过这个标签。

  条件不满足时（例如面单比视野还宽），如实记为 `failed`，不武断判为无码。Harness 成功条件改为"每个条目是 `scanned` 或 `unreadable`"。
- 下蹲补看改为对所有能看全该面底部的下蹲档位取并集。改后的第一次运行里，正面在观察阶段就把 3 个真码全部纳入了计划。
- `next_barcode` 每次都先从当前位置重看并更新计划，不再依赖 LLM 自觉调用 `plan_scans`。
- 中间几轮（v2–v6，每轮发现问题即停、修复后重跑）暴露的执行问题：
  - 真码被误判为 `unreadable`：枪口偏轴时标签有一半在视野外。改为要求整个标签在视野内；在预备位（约 0.4 m）读到过、到最终位读不到时，退回预备位补扫一次。
  - 手臂没到扫码距离就扫码：就位检查只在枪口确实在扫码距离上时才提示"现在扫码"。
  - LLM 跳过 `move_arm('final')`，被检查提示误导，反复重新规划站位：现在按手臂实际收到的命令给提示。
  - LLM 跳过 `next_barcode`，直接操作下一个码，陷入循环直到上下文溢出：任务 3 的条码工具只接受当前条码；"同一调用反复失败"按调用（工具 + 参数）计数。
  - LLM 失控生成，超时后被 SDK 原样重发：超时按生成到上下文上限所需时间重设，截断或超时后用模型自带的采样配置重新生成。详见[LLM 服务与客户端](llm.md)一页。

**结果（同一场景）。**

| | 首轮（修复前） | 最终轮 v7（修复后） |
|---|---|---|
| 真码扫到 | 4/6 | 6/6，每面顺序与真值一致 |
| 面的顺序 | 正面先扫、各面连续 | 正面先扫、各面连续、四面都走到 |
| 读错 / 重复读 | 0 / 0 | 0 / 0 |
| 枪尖误差 | — | 平均 1.0 cm，最大 1.8 cm |
| 用时 | 4055 s | 6778 s |
| LLM 截断 | 0 | 1/460 次（0.2%），已重新生成 |

**代价与遗留问题。**

- 用时变长，原因是系统要逐个走近核验 32 处贴纸，平均每处约 2 分钟。按目前的证据，从头部相机无法提前排除它们。
- 按评测器（真值）是 6/6 成功，但 Harness 自己报告失败：有 15 处贴纸核验不了，要么比视野还宽，要么位置太低。真实场景里事先不知道哪些是贴纸，所以成功定义需要需求方决定：是"所有可读的码都扫到"，还是"所有标签都给出结论"。这一点还没定。

## 已知限制

- **结果证据薄。** 任务 3 的每个箱堆场景都只跑过一次。v10 加的修改（`unreadable`、只接受当前条码、扫完自动重看、按调用计数失败等）没有在之前跑通的场景（桌面任务、stack3、stack9、stack4f）上重跑，可能影响原来的结果。成功率还没有给出 ± SE。
- **任务 1、2 的批量评测不完整。** rule 模式批量运行按决定提前停止，只覆盖部分 L1 套件。L2 套件和 `agent_assist` / `agent_full` 的批量结果都没有。大箱子场景（`t1_L1_box_shape_0007`–`0011`）的任务 1 失败没有修。
- **任务 1、2 的成功只看就位，不看扫码。** 任务 2 的评测不调用扫码枪；只有任务 3 要求读出内容。
- **任务 1 的距离误差相对 Harness 自选的 d_obs 计算。** `d_err_m` 比较的是实际离面距离与 Harness 选的 d_obs，不是与真值观察位比较。真值观察位的偏差只出现在 `perception_err_pos_m` 中，不参与判定。
- **只看到一个箱子时无法区分左右。** 任务 1、2 的 `select_target_box('left'/'right')` 在只看到一个箱子时直接失败（`t2_L1_box_lateral_0010` 即此例）。
- **rule 模式的探索序列含两步必被拒绝的动作。** `right 1.0` 和 `turn_right 30` 超过单步上限 0.5 m / 15°，`explore` 每次都会拒绝。v3 时就已发现，还没决定拆分还是删去。
- **成功定义未定。** 有贴纸时，Harness 判定（所有标签都要有结论）和评测判定（所有真码都读到）不一致，需要需求方决定（见 v10）。
- **晚发现的码可能破坏顺序。** 计划可追加，但如果新码发现得晚、位置却在已扫码的左边或上方，只能排到当前之后；评测器按完整真值顺序判定，这时 `order_ok` 为假。目前的测试里没有观察到这种情况。
- **`max_m 0.30`、`budget.max_wall_s 1800`、`approach.move_timeout_s 20.0`、`approach.max_segments 8` 等配置值没有给出依据。**
- **可达范围限制了场景。** 扫码枪必须水平且与条码对齐时，码中心要不低于约 0.27–0.33 m（不同场景的结论见 v5、v8）。更低的码只能报 `unreachable`。
- **尚未测试的场景。** `stack4c_L0_0000`（纸箱四面都有码）、`stack4c_L0_0002`（两面各 30 个码）、`stack9c_L0_0000` 都没有运行记录。按 v10 的速度（每处贴纸约 2 分钟），`stack4c_L0_0002` 一次可能要十几个小时（推测），需要先提速，例如一个站位只动手臂依次核验多个相邻标签。
- **头部相机参数还没和真机标定。** 测试集任务 2 的起始位姿用的是仿真包 `g1_barcode_sim/configs/testsuite/head_camera_nominal.yaml` 中的标称参数。
