# 开发时间线

本页按时间顺序记录 g1_agent_system 从 2026-11-05 到 2026-11-09 的全部更新，包括它所依赖的仿真环境（g1_barcode_sim）中直接影响 agent 的改动。每天一个小节，天内按时间排列；每条的格式是 **时间 · 组件 · 类型**，组件名链接到对应的说明页，类型取「需求 / 决策 / 初版 / 问题 / 修复 / 改进 / 重构 / 实验结果」之一。同一件事在不同记录中出现多次时只保留一条，并把各处的细节合并进来；时间取自开发日志，均为 UTC（比美国太平洋时间早 8 小时）；2026-11-08（UTC）当天只有对前一天工作的回顾，已全部并入 11-07 的对应条目。所有数字来自运行记录和测试输出；文中的路径都是仓库内相对路径。

项目贯穿始终的几条设计原则也会在下文反复出现：LLM 生成不设输出长度上限，被截断的回复不解析、重新生成；不引入没有数据或规格依据的阈值，凡是手定的数值都单独说明；不用宽泛的 try/except 吞掉错误；修 bug 先找根因，按原理修复，而不是针对某个失败样本打补丁。

## 2026-11-05

**09:43 · [任务定义](tasks.md) · 需求** 搭建 G1 扫码仿真 —— 需求是在 Isaac Sim + Isaac Lab 中搭一个 Unitree G1 29-DoF（Dex1 两指夹爪）在工厂里找纸箱条码的仿真，提供 3 个可切换场景（白桌两箱、货架多箱、地面堆成与 G1 同高的立方体），条码贴在朝外侧面、中心离地不高于 1.3 m；环境要给出与真机对齐的头部 RGB-D、root 速度控制接口和条码真值。本期不做扫码枪、手臂 IK 和找码算法，这三部分后来正是 agent 系统要完成的工作。

**09:48 · [系统总体结构](architecture.md) · 决策** 仿真与其他任务共用一张 GPU —— 盘点时可用的 GPU 都已被排队系统租出，需求方决定：仿真不排队，在不影响原有进程的前提下与已有任务共用一张 GPU；重数据放大容量数据盘，代码和报告放在仓库。实测单个仿真进程占 4.5–4.9 GB 显存、约 20% 算力。同日还约定所有汇报统一发邮件，为此写了 scripts/send_report.py（固定收件人和标题前缀、支持附件、超过 24 MB 拒发）。这套 GPU 共享策略后来一直沿用到 agent 的仿真进程和 vLLM 服务。
